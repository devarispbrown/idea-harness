1. Product Definition
idea-harness is a local-first AI product-development control plane that helps a user take an idea from
ambiguity to verified software using a coordinated team of Staff-level AI experts.


The product begins with:


       I have an idea.


not:


       I have a Git repository.


It coordinates research, product thinking, design, architecture, quality, security, planning, implementation,
review, and verification while preserving enough evidence and provenance to explain why important
decisions and implementation choices exist.


The default lifecycle is:



  Explore
     ↓
  Define
     ↓
  Design
   ┌──────────────┬──────────────┬─────────────────┐
   │ Architecture │ Product / UX │ Verification                   │
   │                        │ Design       │ Design               │
   └───────┬──────┴───────┬──────┴────────┬────────┘
               └───────────────┼───────────────┘
                                     ↓
                                Converge
                                     ↓
                                  Build




                                                      1
                                    ↓
                                 Verify
                                   ↓
                                 Done


High-risk initiatives dynamically introduce specialists such as Security, Privacy, Database, SRE, Developer
Experience, Payments, or AI Security.


The user should experience this as:



  I provide direction.
  The system explores.
  The experts challenge each other.
  The system synthesizes.
  I make the important calls.
  The system plans.
  Agents execute.
  Reviewers challenge the work.
  Evidence proves the result.


The product must not feel like managing a Kanban board full of AI agents.

4. Product Principles
4.1 Calm on the surface, rigorous underneath
Routine usage should expose:


     • the current idea
     • what has been learned
     • what is unresolved
     • what needs human judgment
     • what changed
     • what happens next

The machinery behind these outcomes should be progressively disclosed.




                                                   4
4.2 Start before Git
Supported starting conditions:


       • empty folder
       • folder containing notes
       • existing codebase without Git
       • local Git repository
       • remote-connected repository

Git is optional infrastructure.




4.3 Decisions over agent conversations
The system should coordinate experts for the user.


When experts disagree, idea-harness should synthesize the conflict into a human decision surface.


Bad:



  Chat with PM
  Chat with Architect
  Chat with Designer


Good:



  DECISION NEEDED


  Should sharing links expire?

  Product recommends:
  Optional expiration

  Security recommends:
  Expiration by default

  UX recommends:
  No expiration unless selected

  Orchestrator recommendation:
  30 days by default, with "Never" available

  [Accept]




                                                     5
  [Choose alternative]
  [Discuss]




4.4 Staff-level by contract
Role quality must come from:


     • explicit competencies
     • required behaviors
     • artifact requirements
     • review rubrics
     • regression evals

not merely prompts saying "act like a Staff PM."




4.5 Adversarial by default
The development loop is:



  propose
     ↓
  challenge
     ↓
  revise
     ↓
  approve
     ↓
  execute
     ↓
  challenge again


Every material execution plan is independently reviewed.


Every source ChangeSet is independently reviewed.


No agent may approve its own work.


Review depth may vary by risk.




                                                    6
4.6 Risk determines ceremony
A documentation edit and an authentication migration must not receive identical process depth.


Risk controls:


      • review breadth
      • specialist involvement
      • verification breadth
      • model quality
      • human approvals
      • context breadth
      • rollback requirements

Review remains mandatory.




4.7 Deterministic evidence beats probabilistic judgment
If something can be conclusively checked by:


      • compiler
      • test
      • type checker
      • linter
      • schema validator
      • security scanner
      • deterministic command

that evidence should be preferred over LLM judgment.




4.8 Humans make consequential judgments
The system should optimize human attention for:


      • ambiguous product tradeoffs
      • accepted risk
      • irreversible changes
      • high-impact decisions
      • unresolved expert disagreement

It should not create approval fatigue.




                                                    7
4.9 Everything meaningful should be explainable
Users should be able to ask:



  What is this?
  Why does this exist?
  Why did this happen?
  What depends on this?
  Where did this come from?
  What changed?


Product concepts:



  Explain
  Why
  Impact
  Trace
  What Changed




5. Primary User
Initial target:


      • technical founder
      • founder who codes
      • staff engineer
      • technical product leader
      • independent developer
      • very small AI-native product team

The first product must be exceptional for one sophisticated user working locally.


Multi-user collaboration is not required for v0.1.




6. Primary Jobs to Be Done
JTBD 1

When I have an idea, help me turn it into a coherent product definition without requiring me to manually
orchestrate AI agents.




                                                      8
JTBD 2

judgment.


JTBD 3

When agents design or implement something, ensure they challenge weak assumptions and follow my
standards.


JTBD 4

When implementation changes source code, isolate and independently review that change before accepting
it.


JTBD 5

JTBD 6

JTBD 7

When something fails, explain the cause, impact, and available recovery path.

8. Current Understanding
Every Initiative maintains a synthesized projection called Current Understanding.


It represents the most current approved view of:


      • what is being built
      • target user
      • problem
      • desired outcome
      • major constraints
      • important decisions
      • unresolved assumptions
      • open questions
      • major risks

It is not an independent authoritative artifact.


It is derived from approved Product Graph state.


Example:



  CURRENT UNDERSTANDING

  We're building a local-first tool that extracts product
  decisions from meeting transcripts and preserves their
  source provenance.

  Primary user
  Product teams running frequent cross-functional meetings.

  Core value
  Prevent decisions from disappearing into meeting history.




                                                   10
  Key decisions
  • Extracted decisions remain linked to transcripts.
  • Human corrections override AI extraction.
  • Slack ingestion is deferred.


  Still unresolved
  • Conflict resolution semantics
  • Data-retention policy


Acceptance Criteria

     • Current Understanding updates after approved material changes.
     • Draft or rejected agent work cannot silently modify it.
     • Each statement can be traced to its authoritative source.
     • Users can inspect why a statement appears.

52. Final Product Definition
idea-harness is a local-first product-development control plane that takes an idea, builds and
continuously updates a shared understanding of the problem, assembles the appropriate Staff-level
experts, exposes the consequential decisions that require human judgment, creates traceable
product and technical plans, safely delegates execution, independently reviews every proposed
source change, verifies the implementation against its requirements, and can explain why every
important decision and change exists.


The defining user experience is:



  Show me the idea.

  Show me what we've learned.

  Show me what changed.

  Show me what still isn't known.

  Show me what needs my judgment.

  Show me what happens next.

  Hide the machinery until I ask for it.
