# DX Audit — Fix Plan

Source: full 14-stage developer-experience audit of `6b275f5` (verdict **FAIL**, Overall DX 60/100).
Two hard gates fail — `BROKEN_CANONICAL_INSTALL`, `UNEXPLAINED_ERROR` — plus a third P1 of equal
weight (`--json` contract broken, including on state-changing commands).

Every claim below was re-verified against this tree before writing; file:line references are from
`6b275f5`. Where the plan proposes something that does **not** exist yet, it says so.

## Constraints this plan works under

1. **A UI redesign is in flight on `main`** (`web/src/styles.css` modified, `design_handoff_idea_harness_ui/`
   untracked at audit time). Anything this plan does to `web/` or generated UI assets must be
   mergeable with that work, not a collision with it. See *Coordination* below.
2. **One canonical path** (DX principle). The fix is not "document both install routes better"; it is
   "make one route work".
3. **Each fix is one commit**, `go vet ./...` + `go test ./...` + `scripts/smoke.sh` green before the
   next — the CONTRIBUTING loop (§14, §75).
4. **No behavior change without a test that would have caught the bug.** Every track below names its
   regression test; a track without one is not done.

## Track A — Install and local dev (P1 gate + P2)

**Problem (verified).** `.gitignore:20` ignores `internal/web/dist/`; `internal/web/web.go:12` is
`//go:embed dist`. A clean checkout therefore cannot compile at all:

```
$ go install ./cmd/idea
internal/web/web.go:12:12: pattern dist: no matching files found
$ make test        # same error, [setup failed] on 3 packages
$ make vet         # make: *** [vet] Error 1
```

`README.md:81-83` calls `go install ./cmd/idea` the *recommended* route, and `README.md:73-74`
(repeated at `:180` and `docs/architecture.md:22`) tells the reader Node/pnpm is optional "because
the binary already embeds a built UI". Both are false for every fresh clone. CI never sees it
because `.github/workflows/ci.yml` runs `make embed-web` first.

**Decision: commit the built UI to `internal/web/dist/`.**

The embed directive is a compile-time dependency on generated bytes. Either those bytes are in the
repo, or every Go build depends on a Node toolchain. Committing them is the only option that makes
`go install`, `go test`, `go vet`, and `go build` all work from a bare checkout with no Node
installed — which is exactly the audit's acceptance test.

Work items:

1. Configure deterministic asset names in `web/vite.config.ts`
   (`build.rollupOptions.output.{entryFileNames,chunkFileNames,assetFileNames}` → `assets/index.[ext]`,
   no content hash). Today's hashed names (`index-BZOUO_42.css`) would make every UI change a
   delete+add pair and a guaranteed merge conflict; stable paths make it a normal diff.
   Cache-busting moves to the server: `internal/web/web.go` sets `Cache-Control: no-cache` on
   `index.html` and a long max-age on `assets/*`, keyed off the build stamp from Track G.
2. Remove `internal/web/dist/` from `.gitignore`; commit the built output.
3. `make embed-web` keeps working unchanged (`rm -rf` + `cp -r`); it now produces a diff instead of
   untracked files.
4. CI gains a **freshness check**: `make embed-web && git diff --exit-code internal/web/dist` — a
   committed `dist` that no longer matches `web/src` fails the build.
5. CI gains a **no-Node install job**: clean checkout, `PATH` scrubbed of Node/pnpm, `go install
   ./cmd/idea`, start the daemon on a scratch `IDEA_HARNESS_STATE`/`IDEA_HARNESS_ADDR`, assert
   `GET /` returns 200 and the body contains the app root element.
6. Fix the three prose claims (`README.md:73-74`, `README.md:180`, `docs/architecture.md:22`) to
   match: Node/pnpm is needed **only to change** the UI, not to build or install the binary.
   `README.md`'s Option A becomes the single canonical route; Option B becomes "rebuilding the UI".
7. `make test` and `make vet` need no `embed-web` dependency once `dist` is committed — the P2
   local-dev finding dissolves with the P1 gate rather than needing its own Makefile hack.

**Risk, stated plainly.** Generated bytes in git is a real cost: ~210 KB per UI change, and the
freshness check can go red on a Node/pnpm version bump that changes output byte-for-byte. Mitigation:
pin `packageManager` in `web/package.json` and the Node version in CI (already `22`), and compare
after a normalizing build rather than trusting incidental whitespace. If the freshness check proves
flaky in practice, downgrade it from a gate to a warning and rely on the no-Node install job, which
is the one that actually protects the gate.

**Alternative considered and rejected:** committing a placeholder `index.html` stub so the embed
resolves. It satisfies "HTTP 200" while serving a UI that is not the product, and `make embed-web`'s
`rm -rf` deletes the tracked stub on every build — a wart in the inner loop for a hollow pass.

**Test:** the two CI jobs above. Both are new; neither exists today.

## Track B — CLI contract: flags, `--json`, exit codes (P1)

**Problem (verified).** `resolveInitiative()` (`internal/cli/advance.go:26-28`) returns `args[0]` as
an initiative id with no flag filtering:

```go
if len(args) > 0 {
    return args[0], nil
}
```

So `--json` becomes the lookup key, the daemon misses, and the CLI prints the store's raw error.
Observed on a fresh project: `tasks`, `changes`, `risk`, `explain`, `why`, **`advance`** → exit 1
`idea: sql: no rows in result set`; `plan`, `verify` → exit 0 with the flag silently ignored.
`advance` and `execute` are state-changing, so this is not only a rendering failure — a flag typo
aims a workflow transition at an initiative that does not exist.

Call sites that inherit it: `advance.go:38` (`cmdAdvance`), `:65` (`cmdTasks`), `:158` (`cmdDiff`),
`:201` (`runTraceCmd` → `why`/`impact`/`trace`), `change.go:58` (`cmdExecute`), `:117` (`cmdChanges`),
`:237` (`cmdRisk`). Two commands inline the same defect instead of calling the helper:
`explain_export.go:34` (`cmdExplain`, which also never calls `wantJSON`) and `watch.go:18`
(`cmdWatch`). Only `docs.go:34-39` filters flags, ad hoc.

Work items:

1. Add one parser in `internal/cli/state_cmds.go` beside `wantJSON` (`:77`):
   `splitArgs(args) (positional []string, flags map[string]string)` — everything with a `-` prefix is
   a flag, never a positional. `wantJSON` becomes a lookup on the parsed flags.
2. `resolveInitiative` takes positionals only. Every call site above passes `splitArgs(args)`'s
   positional slice. `cmdExplain` and `cmdWatch` stop inlining and call the helper.
3. Every state-returning command honors `--json` or rejects it — no silent ignore. `cmdExplain` gains
   `wantJSON`/`dumpJSON`. `cmdPlan` (`advance.go:55`) delegates to `cmdExport`, which emits markdown;
   it either gains a JSON envelope (`{"kind":"execution_plan","markdown":"…"}`) or fails with
   `--json is not supported for plan; use idea tasks --json`. **Pick one and apply it uniformly** —
   the audit's complaint is the silence, not the choice.
4. An unknown flag on any command is an error naming the command's accepted flags, not a positional.
5. `cmdNext` (`next.go:12`) currently ignores `args` entirely; it goes through the same parser.

**Test:** a table test in `internal/cli` over every state-returning command × `--json`, asserting
exit 0 and `json.Valid(stdout)`; a second table asserting an unknown flag exits non-zero and never
reaches the daemon. This is the test that would have caught the bug and does not exist today —
`internal/cli` holds only `docs_test.go` and `executor_setup_test.go`.

## Track C — Error surfacing (P1 gate)

**Problem (verified).** `idea apply CHG-99` and `idea review CHG-99 approve` both answer
`idea: sql: no rows in result set` (exit 1). `cmd/idea/main.go:12-15` prints whatever error reaches
it, so the driver string is the product's error message.

The mapping already exists: `changeSetRefError()` (`internal/daemon/handlers.go:1400-1405`) turns
`sql.ErrNoRows` into `"change set not found"`, and `handleGetChangeSet`/`handleChangeSetDiff` use it.
The leak is that the three shared lookup helpers return the store error unmapped —
`s.changeSet` (`handlers.go:1389-1396`), `s.initiative` (`:1429-1436`),
`initiativeFromQuery` (`:1440-1454`) — and their callers pass it straight to
`writeError` (`server.go:165`).

Work items:

1. Map inside the three helpers, so all ~10 callers inherit it in one place. Not at each call site.
2. Echo the reference the user typed: `no change set matching "CHG-99"`, `no initiative matching
   "…"` — matching the shape the product already uses well
   (`no requirement matching "REQ-9"`, `no project registered for …; run \`idea init\` first`).
3. Not-found is 404, not 500 (see Track F).
4. Errors that are not `sql.ErrNoRows` keep their text; this is a mapping, not a swallow.

**Test:** a daemon handler test asserting 404 + the friendly body for an unknown id on every
`{id}`-taking route, and a CLI test asserting no error string ever contains `sql:`. The second is the
one that generalizes — it fails on the next leak from anywhere.

## Track D — Config and model validation (P2)

**Problem (verified).** `idea model set bogus/model` → `✓ default model set to bogus/model`;
`idea config validate` → `config: valid`; `idea doctor` → `all checks passed`. No provider `bogus`
exists. `config.Load` (`internal/config/config.go:178-186`) validates `Network`, `Executor.Kind`, and
`Review.MaxCycles`, never that `default_model`'s provider resolves. `ResolveProvider`
(`internal/config/providers.go:56-75`) defaults any unknown key to `openai` with no key-env, so it is
never even "not ready". `handleUpdateProviders` (`handlers.go:283-330`) writes without checking.

Work items:

1. New `Config.Problems() []Problem` (severity `error` | `warn`): unknown provider prefix in
   `default_model` = error; known provider with an unset key env = warn (demo mode is legitimate).
2. `idea config validate` and `cmdDoctor` (`internal/cli/cli.go:418-432`) both render it. `cmdDoctor`
   already calls `config.Load` at `:427`, so it inherits the check for free.
3. Reject at the write path too: `idea model set` and `handleUpdateProviders` refuse an unknown
   provider, naming the configured and preset providers.
4. **`config.Load` itself keeps loading.** Turning this into a load error would brick an existing
   project on upgrade — a config that is wrong should be *reported*, not *unopenable*.

**Test:** table test over `{unknown provider, known provider without key, valid}` asserting the
severity from `Problems()`, the exit code from `model set`, and the `doctor` line.

## Track E — Documentation sync (P2)

**Problem (verified).** `docs/cli.md` documents 16 commands; `internal/cli/cli.go:31-101` dispatches
~38. Missing: `advance`, `plan`, `tasks`, `execute`, `changes`, `change`, `apply`, `revert`, `review`,
`verify`, `next`, `risk`, `why`, `impact`, `trace`, `diff`, `docs`, `executors`, `cancel` — the whole
M2–M4 loop the reference exists to describe. Four (`risk`, `diff`, `cancel`, `change <id>`) appear in
no document at all. Separately, `docs/configuration.md`'s `harness.yaml` table has no `git_commit`
entry, though `internal/config/config.go:116` defines it and README, quickstart, and `docs/ui.md`
all tell you to set it.

Work items:

1. `idea help` becomes the single source: a `--format=md` mode (or a small `go run ./internal/cli/gen`)
   emits the command table, and `docs/cli.md` embeds the generated block between markers.
2. CI check: regenerate and `git diff --exit-code docs/cli.md`. A new command with no doc line fails
   the build — the drift class, not just today's instance.
3. Hand-written prose per command stays hand-written; only the table is generated.
4. Add `git_commit` to `docs/configuration.md`'s field table.

**Test:** the CI drift check itself.

## Track F — Daemon API consistency (P2)

**Problem (verified).** Business-rule violations return 400 from `handleVerify` (`handlers.go:1130`,
`:1138`) and `handleReviewChangeSet` (`:1226`), but 500 from `handleExecute` (`:1104`), `handleNext`
(`:1164`), `handleResume`/`handleApprove` (`:201`, `:215`), `handleApplyChangeSet`/`handleRevertChangeSet`
(`:1243`, `:1259`). A client cannot distinguish "you asked for something invalid" from "the daemon
broke". Addressing is split two ways: `tasks`/`why`/`impact`/`trace`/`diff` nest under
`/initiatives/{id}/…` (`routes.go:26-30`) while `change-sets`/`risk` are flat with `?initiative_id=`
(`routes.go:66,72`). `/initiatives/{id}/next` (`:65`) and `/initiatives/{id}/next-move` (`:17`) are
near-identical names with unrelated semantics.

**Scope split, deliberately.**

- **In scope now (non-breaking):** status-code correction. Domain rule violations → 4xx with a
  stable body shape; infrastructure failures stay 5xx. A handler test asserts the class per error
  type. The CLI already renders `{"error": …}` (`server.go:165-167`), so no client change is needed.
- **Deferred (breaking, and it collides with the UI work):** route unification and the
  `next`/`next-move` rename. Both change URLs the React app calls, and `main` currently has a UI
  redesign in flight. Doing this now means resolving the same conflict twice. It gets its own plan
  after the redesign lands, with the two routes versioned or aliased through one release.

**Test:** handler table test mapping each error type to its expected status class.

## Track G — Version, changelog, releases (P2)

**Problem (verified).** No `idea version` (not in the `cli.go` switch), no git tags, no `CHANGELOG`,
no upgrade or migration guidance. Every install is "whatever `main` was that day" and a bug report
cannot name a build. Lowest-scoring area in the audit (30/100) and the cheapest to lift.

Work items:

1. `idea version` prints version, commit, and build date. Two sources, one command:
   `-ldflags -X` from the Makefile for tagged builds, and `runtime/debug.ReadBuildInfo()` for
   `go install` builds (which stamp `vcs.revision` automatically). Neither alone covers both routes.
2. `--version` and `-v` alias it; `idea doctor` prints the same stamp so bug reports carry it.
3. `CHANGELOG.md`, Keep-a-Changelog shape, starting at the first tag. Pre-1.0 versioning policy
   stated in one paragraph in `README.md`.
4. First annotated tag `v0.1.0` cut **after** Tracks A–C land, so the first release is one where the
   documented install works.

**Test:** a smoke assertion that `idea version` exits 0 and matches `v?\d+\.\d+\.\d+|[0-9a-f]{7,}`.

## Track H — Testing the surface the product actually is (P2)

**Problem (verified).** 43 Go test files, green in ~12 s — but `internal/cli` holds two of them, and
no test anywhere passes `--json`, which is why Track B's bug shipped. `scripts/smoke.sh` paces an
async daemon with fixed `sleep 3`/`sleep 2` calls (lines 56, 66, 74, 82) and asserts human output
only.

Work items:

1. Golden-output tests per command, both renderers (human + `--json`), against a fixture project.
   Tracks B, C, D each land their slice; this track is the harness they share.
2. `scripts/smoke.sh` waits on state, not the clock — poll `idea status`/`idea changes` with a
   deadline, the way the script's own daemon-health loop (lines 24-27) already does correctly.
3. CI runs the suite on macOS as well as ubuntu. The audit ran on darwin/arm64; CI has never.

**Test:** the suite is the test. A CI matrix entry proves the second item.

## Track I — Real-value path (P2)

**Problem (verified).** Out of the box the pipeline is demo mode + the internal placeholder executor:
`Synthetic demo PRD for: …` and a `hello.txt` placeholder. The governance machinery around it is
real and was verified end-to-end (apply → `hello.txt` → byte-for-byte revert → `✓ initiative
complete`). The labeling is honest and prominent, which is why this is P2. But the 15-second magic
path proves the control plane, not the product's claim, and the route to real value — provider key
plus a Hermes/OMP executor — has no documented budget and no measurement.

Work items:

1. `docs/quickstart.md` gains a second, explicitly timed section: real provider + real executor, with
   the expected wall-clock and the cost order-of-magnitude.
2. The existing opt-in `agent` CI tier (`ci.yml`, `workflow_dispatch`, already holds
   `ANTHROPIC_API_KEY`) records and prints that elapsed time, so the number is measured, not claimed.

**Test:** the CI tier's own assertion, plus a documented number that a reader can check.

## Track J — P3 batch (one commit)

`idea apply CHG-1` on an already-applied set returns `✓ apply started` with no idempotency signal ·
`idea status` on a complete initiative still prints `→ Resolve open questions` · two error-string
shapes from the same daemon (bare at `client.go:66`, `"daemon: "`-prefixed at `:139`) · no HTTP API
reference in `docs/` · magic path costs 13 commands against a target of 8.

The last one is a design question, not a bug: `idea next` already knows the sequence and could carry
more of it. It is listed, not scheduled.

## Out of scope

Route unification and the `next`/`next-move` rename (deferred in Track F, with reason) · SDKs ·
OpenAPI generation · anything touching `web/src` beyond `vite.config.ts` · the `idea watch` exit-code
claim, which the audit could not reproduce headlessly and is recorded as source-based only.

## Coordination with the UI redesign

Track A touches `web/vite.config.ts` and adds `internal/web/dist/` to the tree — both of which the
redesign branch will also produce. Sequence: land Tracks B–E on this branch first (pure Go + docs,
zero overlap), and rebase Track A onto `main` **after** the redesign merges, regenerating `dist` from
the merged `web/src` as the final step of that commit. If the redesign will not land soon, Track A
goes first anyway and the redesign rebases — but that call is the user's, not this plan's.

## Sequencing

| # | Track | Depends on | Why here |
|---|---|---|---|
| 1 | B — flag parsing | — | Pure Go, no conflict surface, unblocks the `--json` tests everything else uses |
| 2 | C — error mapping | — | Same; the two P1s that need no coordination land first |
| 3 | H (harness only) | B, C | Golden-test scaffolding both tracks feed |
| 4 | D — config validation | H | Uses the harness |
| 5 | E — doc generation | B | Command table generated from the parser B just cleaned up |
| 6 | G — version + changelog | — | Independent; needed before the first tag |
| 7 | A — install gate | UI redesign merge | Highest severity, highest conflict risk — see Coordination |
| 8 | F — status codes | — | Non-breaking half only |
| 9 | I, J | A | Documentation and polish once the install story is true |

Track A is first by severity and last by sequence. That is deliberate and it is the plan's main
tension: the gate that fails hardest is also the one that collides with in-flight work.

## Definition of done

- Tracks A–H implemented; I and J landed or explicitly deferred with a dated note.
- `go vet ./...`, `go test ./...`, `bash scripts/smoke.sh`, `cd web && pnpm build && pnpm test` green.
- The three new CI jobs pass: no-Node install, `dist` freshness, `docs/cli.md` drift.
- A re-run of the audit's journey manifest returns **PASS** or **PASS WITH DEBT**: both P1 gates
  clear, `--json` valid on every state-returning command, no CLI error containing `sql:`.
- This plan adversarially reviewed before implementation (§14), with blocking findings resolved in
  the text.
