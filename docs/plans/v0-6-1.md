# v0.6.1 and v0.7.0: what the five founder journeys and two outside harnesses say to do next

Source: the five ICP founder journeys run against v0.5.1 → v0.6.0 (verdicts
trial → hold → hold → trial → trial → adopt), the whole-branch adversarial
review of `efac66d..HEAD`, and two comparable systems:

- **bassclef** (`docs.bassclef.dev`), a Claude Code add-on with the same arc
  (`/riff` → `/launch` → `/build`). File-based state, a documented
  failure-mode catalogue, and "luminaries": 98 practitioner profiles routed in
  as a domain lens per task. Its own docs state no cost, context-management or
  determinism properties, so only its *surface* is evidence here, not its
  rigor.
- **Stripe's Minions** (public write-ups), ~1,300 AI-written PRs a week:
  narrow tasks, a structured task spec that carries the code the agent needs,
  agents that iterate against tests inside a sandbox before opening a PR,
  human review before merge.

Everything below is traceable to an observed failure in one of our own runs.
Where it is only an idea from one of those two systems, it says so.

## What the journeys actually showed

| Observed | Where | Consequence |
|---|---|---|
| The implementer wrote Python for a Go project | re-run 1 | a wasted paid run |
| It restructured an 80-line service into `cmd/` + `internal/` unasked | re-run 5 | a 15-file diff for a one-endpoint task |
| It downloaded a Go toolchain into the workspace | re-run 2 | ~14,300 files collected, 79 false secret findings, a diff endpoint that did not answer in 100 s |
| 0 of 8 executes produced an applicable change set | re-run 1 | verdict "hold" |
| Checks ran only *after* the agent exited | every run | a failing test costs a whole new agent run |
| A 15-file / ~26 KB diff hit the reviewer's output ceiling | probe 2 | the review wedged until the ceiling was raised |
| Plan edits had no CLI verb | re-runs 3 and 5 | the evaluator fell back to raw HTTP |
| `agent: not measured` | every run | ~24 minutes of agent time unpriced per run |
| Six distinct failure modes, each diagnosed from source by an evaluator | all runs | no user-facing page says what to do |

## v0.6.1 — cheap, from evidence in hand

### A. `docs/failure-modes.md`

bassclef's format, which is the part worth copying: **symptom → diagnostic
command → expected output → recovery**, one block per class. Seed it with the
six we have already fixed and can therefore describe honestly:

1. A change set whose adversarial review never completed (stopped mid-review).
2. A change set rejected by the secret sweep, and what `not_a_secret` does.
3. A no-op (zero-file) change set.
4. A revert refused because the workspace moved on.
5. A review that truncated at the model's output ceiling.
6. A task that will not re-run because an earlier change set is unresolved.

Classes 1 and 6 are the **same root cause** (`execute.go`'s
`Status == ChangeSetReviewRequired && !ReviewCompleted()` guard) presented from
two symptoms; the page says so rather than implying six mechanisms.

Each block names the real command (`idea status`, `idea reviews`,
`idea review <id> rerun`) and the real message. **Acceptance:** a docs test
asserts every block's quoted message still matches the code that emits it.
Several of those messages are `%s`-templated (`ReviewNeverCompletedCause()`,
the revert refusal's three slots), so the test matches the format string with
wildcards, not a rendered example; it also anchors against
`internal/cli/testdata/help.txt`, which is already generated and golden. This
is what stops the page rotting the way `README.md`'s CLI claim did.

### B. A brief that carries the code (Stripe's "spec quality bounds output")

Today `runPlanner`'s brief names the detected stack, the project scale, the
resolved decisions and answers, and the detected check commands. It does not
carry the code. Add, bounded and deterministic:

- **Excerpts of the files the task will touch.** Resolve them from the task's
  requirement → the files its acceptance criteria name, plus the files the
  previous change set for this initiative touched. Cap the total (a budget in
  characters, not files) and say in the brief that it is an excerpt.
- **The project's existing test patterns.** One real test file from the
  repo, chosen as the nearest neighbour of the files above, so the agent
  matches the house style instead of inventing one.
- **An explicit non-goal line:** do not restructure the project, do not add
  dependencies, do not install a toolchain. The last of those already exists
  verbatim in `runPlanner`; the first two are new and each is a logged failure.

**Two gaps the plan review found, which B does not ship without.**

- **Excerpts must be redacted before they are sent or stored.** The sweep
  (`scanWorkRootForCredentials`) runs on the agent's *output*, after the run.
  The brief is built and persisted as a durable Run *before* any agent runs, so
  an excerpt from a file holding a realistic key (a fixture, a
  `.env.example`) would go to the provider and into the stored brief through a
  path the sweep never touches. Excerpts pass through `internal/security`'s
  patterns first. **Acceptance:** a test that a matched value is masked both in
  the live prompt and in the persisted Run.
- **Resolution is empty on the first task of a fresh initiative**, which is the
  case that matters most: `AcceptanceCriterion` is `{Metric, Target,
  Condition}` with no path field, so "files the criteria name" is prose
  scraping, and "files the previous change set touched" does not exist yet. The
  fallback is stated in the plan and tested with a task-1-of-a-fresh-initiative
  fixture: fall back to the files the detected stack's entry points name, and
  say in the brief that no prior change set existed.

**Acceptance:** a fake-model test asserts the brief contains an excerpt of a
named file and a test-pattern section; a mutation check confirms removing
either fails that test. The character budget is config (`agent.brief_budget`),
documented, and defaults to a value that leaves room for the diff the reviewer
will later read.

### C. A blast-radius guard

Stripe's rule is narrow tasks with a limited blast radius; our own plan aims
for 2–4 vertical slices and then does not enforce anything. A change set that
touches more than `execute.max_files` files or `execute.max_lines` added lines
is **refused before review**, with a message naming the count, the limit, and
the two ways forward (split the task — `POST .../tasks/{id}/split` and now a
CLI verb — or raise the limit). Defaults chosen from observation: the 15-file
diff that hit the review ceiling is the upper bound we know hurts, so the
default sits below it.

The count **excludes** paths already excluded by `fsdiff`'s well-known-dir and
`.gitignore` rules (shipped in 0.6.0 for the toolchain-download failure), so a
lockfile regen or a generated file does not trip a guard meant for
hand-written sprawl. "Lines added" is not a persisted field today; the guard
derives it from the patch manifest at refusal time, or the limit is files-only
— decide in implementation and state which, rather than inventing a column.

Transfer caution: Stripe's blast-radius rule sits inside their own CI and a
human review before merge. We have no human gate before the daemon advances
state, so the cap transfers but "refuse, with two ways forward" is not
equivalent governance by analogy.

This is a guard that starts refusing work that used to pass, so it is a
**BREAKING** row with a Was/Now, per `RELEASING.md`.

**Acceptance:** a test for the refusal and its message; a test that a change
set at the limit passes; a false-positive fixture (one large generated file,
few hand-written lines) that must still pass; and the limit is reachable from
config — the lesson from the `review.max_tokens` defect, where the error named
a knob that did nothing.

### D. CLI verbs for plan editing

`add-task`, `merge-tasks`, `split-task`, `depends-on`, `reorder` — the five the
API and web UI already have and the CLI does not. Argument shapes are the
design work: a split names its replacement tasks and their requirements; a
reorder takes an ordered list. Follows `internal/cli/judgment.go`'s shape, with
`docs/cli.md` and `internal/cli/testdata/help.txt` regenerated.

**Acceptance:** the whole plan-editing journey runs from the CLI with no raw
HTTP. That is exactly what the evaluator could not do twice.

### E. Measure agent spend

`agent: not measured` is honest but it is a cost-governance hole, and it is the
one number a founder asks for. **0.6.0 already ships a first source**:
`AgentCostFromRuns` (`internal/projection/costs.go`) parses the agent's console
output for a `$` figure or token counts, prices tokens from
`internal/model/pricing.go`, and fails closed — it reports a total only when
every run parsed. E extends that rather than starting from nothing. Two further
sources, in order:

1. **What hermes reports.** `--usage-file` is documented against `hermes -z`,
   not the `hermes chat --yolo -q` invocation we use, and nothing in-repo
   references it. Verify against a real container before wiring anything. If it
   works it becomes the preferred source and the console parser stays as the
   fallback; if it does not, say so and stop.
2. **A configured proxy, clearly labelled.** `agent.rate_usd_per_hour` ×
   container wall time, reported as an estimate and never mixed into the
   measured model total. **Ship this regardless of how the spike goes**, so E
   is not contingent on an unverified flag.

**Acceptance:** `idea status` and `GET .../costs` either report a measured
agent figure or say which of the two they are showing. Never a bare number
that reads as the total — the defect we already fixed once.

## v0.7.0 — the one that changes outcomes

### F. Checks inside the agent loop — BLOCKED on a design review

Today: agent runs -> container is removed -> the harness runs build and tests ->
a failure rejects the change set -> the next attempt is a **whole new paid
run**. That sequence is the direct cause of "0 of 8 usable change sets", and
closing it is still the highest-value change available.

The plan review stopped this item from being built as first written. Three
things are true in the code and were not true in the plan:

- **The agent container and the check sandbox are different trust tiers by
  design.** `internal/executor/agent.go` deliberately omits `--network none`
  (the agent needs model egress) and is writable; `internal/executor/sandbox.go`
  sets `--network none`, `--read-only` and `--cap-drop ALL`. "The same toolchain
  image" conflates image with isolation: running a check in the agent's own
  container is not running it in `ContainerSandbox`. A test needing the network
  would pass in-loop and then reliably fail the authoritative check -- breaking
  exactly the case F exists to fix.
- **An agent that can run the check tool can fabricate its output.** It can
  emit a synthetic `go test -json` pass stream without running anything. The
  evidence pipeline's defences (sticky fail, exit code, JSON-only parsing) were
  built against text forgery *within a harness-run check*, not against a second
  writer the agent controls.
- **The harness's own check is not a clean room.** It binds the same host
  directory the agent wrote to, not a fresh checkout. That is already true
  today, so F does not regress it -- but F's prose implied independence it
  never had. The real backstop against a tampered test is the adversarial
  review of the diff, which F does not change.

So F needs its own **design** review before any implementation, scoped to three
questions and nothing else: the network boundary (does the in-loop check run in
a nested hardened sandbox, and can it?), evidence provenance (is the in-loop
output structurally unable to reach a `tests`-category finding or
`ComputeEvidenceTests`?), and whether removing the one-failing-test penalty
pushes diffs toward the review ceiling that item A documents.

**Acceptance, when it is designed:** a fake-agent run whose first attempt fails
tests and whose second passes yields **one** change set and **one** billed
agent run; the authoritative check still runs in the hardened sandbox; a test
proves agent-reported success with a failing harness check still rejects; and a
test proves no code path lets the in-loop output become evidence -- an absence
test, not an outcome test.

### G. Parallel execution of independent tasks — BLOCKED on workspace isolation

The premise in the first draft was wrong in the user's favour: `Engine.mu` is
**engine-wide**, held for the whole body of Execute, ApplyChangeSet and
RevertChangeSet, so it already serializes every initiative in a project -- not
merely every task in one initiative.

Two prerequisites, neither of which exists:

- **A per-task work root.** The work root is keyed by initiative
  (`work/<initiativeID>`) and seeded once from the single workspace root;
  `fsdiff` brackets the agent against that one tree. Two concurrent tasks would
  write the same files and contaminate each other's before/after snapshots,
  producing corrupt or misattributed change sets whatever the claim table does.
  A per-task or per-attempt root (a `git worktree` per task, reconciled at
  apply) is the design work.
- **A decision about which methods keep the coarse lock.** Narrowing Execute's
  lock while Apply keeps it preserves branch-switch safety; narrowing all three
  uniformly makes HEAD-switch races on apply live. The plan must name which is
  which.

Per-task claims are also new state-machine design: only
`ClaimInitiativeRunning` exists. `LatestChangeSetsPerActiveTask` and
`stale_marks` are already per-task and are not blockers.

Treat G as that isolation design first, and parallelism second.

### H. Lenses (bassclef's luminaries, scoped down)

Every phase already runs under a named role. A lens is a short profile -- a
practitioner's stance on one domain -- selected by phase plus detected stack and
injected into that role's prompt. Keep it small and honest:

- A `lenses/` directory of short files, each tagged by domain.
- Selection is deterministic and logged on the run, so a lens is attributable.
- **Rigor-gated**, because prompt bloat is what produced the truncation wedge.
- **Labelled as untrusted input**, like the conventions file -- the hazard
  recorded as M8 in `internal/workflow/rigor.go`'s own comment (there is no
  document by that name; cite the code).
- Never consulted by a deterministic check. Taste informs prose, not gates.

**Acceptance, aimed at the seam that is actually reachable.** The direct
`in_diff: false` assertion is already overridden by `classifyDiffEvidence` when
a finding's path matches the diff; the reachable seam is its **fallback to the
reviewer's self-report when the path is absent or unmatched**. So the test
plants a lens that buries an instruction to misreport a finding's *path*, and
asserts the override still fires by path-matching. Note what this is: the
**first behavioural** test of the untrusted-input label, which until now has
only ever been string-presence tested. If it shows a frontier model partially
complying with a buried instruction, M8 itself needs a fix, and that is in
scope for H rather than a surprise.

## Later

- **Plain-text state export** (`idea export <initiative>`): the graph,
  decisions, change sets and evidence as readable files. bassclef's file-based
  `state/` and `chronicle/` are strictly better for debugging and for review in
  a PR; our SQLite-behind-an-API is opaque, which is why evaluators kept
  dropping to raw HTTP. Export, not migrate: the invariants and transactions
  are worth keeping.
- **A Claude Code-driven mode with no API key**, as bassclef does. The daemon
  runs unattended, so this is an additional executor, not a replacement.

## Order

The plan review's answer, adopted: **A, C and D are the smallest set that could
plausibly move the next journey's verdict.** All three are self-contained and
testable today, they address the two failures an evaluator hit twice (a
15-file diff for a one-endpoint task; falling back to raw HTTP for plan edits),
and none of them touches the check boundary, the evidence pipeline or the
concurrency model.

1. **A, C, D in parallel.** C before B, not after: it is self-contained, and by
   capping sprawl it may already cover re-run 5's worst failure.
2. **B**, once its two gaps are specified together -- excerpt redaction and the
   fresh-initiative fallback. They ship as one unit or not at all.
3. **E**, with the wall-time proxy landing regardless of the `--usage-file`
   spike.
4. **F** only after its design review. **G** only after a workspace-isolation
   design. **H** after that.

Do not expect E, F or G to move the next verdict. A, C and D might.

## Where this plan was wrong

Kept deliberately, because the next round should see what a plan review caught
before anyone wrote code:

- F's safety argument ("the harness still runs its own checks afterwards") did
  not survive the code: two trust tiers, a fabricable in-loop check, and a
  post-hoc check that is not a clean room.
- G assumed per-initiative serialization and reusable per-task claims. The lock
  is engine-wide, per-task claims do not exist, and the work root is shared.
- B would have put unredacted file excerpts into a network-bound, persisted
  prompt, and would have resolved to nothing on a fresh initiative's first task.
- A counted six failure modes where two share one root cause.
- E ignored the cost parser that already shipped in 0.6.0.
- H cited a document that does not exist, and aimed its test at a seam that is
  already closed instead of the fallback that is open.
- Both C and F borrowed a Stripe mechanism without carrying over the human
  review and CI that make it safe there.
